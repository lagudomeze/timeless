## 为什么按领域分文件（而不是一条一个文件）

GitHub 的「一条 issue 一个条目」是为**多人并行、一人一个 PR**设计的；在单人本地仓库里
它换来的是十几个小文件、每次改动落在一堆文件之一。按 `area` 分组之后，
**同一块屏幕 / 同一个领域的改动集中在一处**——这与「按 area 收口」的整治方向一致。

## 条目格式

```markdown
- [ ] **[P0][bug] 一句话说清现象**（原 issue #47）
      **现象/证据**：实机读到什么（坐标 / 读数 / 测试名）。
      **根因**：哪一行、为什么。
      **改法**：动哪个文件、动什么。
      **验收**：要加/改哪条测试，以及**怎么证明它不是空跑**。
      **拍板**（如果有）：需要人决定的事，以及已定的结论。
```

保留「验收」是硬要求：本仓库的规矩是**改回去必须转红**，只写"加个测试"等于没验收。

## 状态标记

- `[ ]` 未完成
- `[x]` 已完成（正文留着，因为验收证据以后还要被引用；**不要**只留下一个勾）
- 结论是「**主动不做**」的条目也标 `[x]`，但必须写清**触发条件**——
  没有触发条件的"不做"等于遗忘。
