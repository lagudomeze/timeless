> ⚠️ **这一版是设计，代码尚未落地**（`src/` 里 grep 不到 `EquippedTo`）。
> 栏目用 ✅ = 已有可复用机制、🚧 = 本文新定、❓ = **需要你拍板**。
>
> 关系模型的通用规则见 [relations.md](relations.md)；数值外置见 [config.md](config.md)。

## 一、这一版要解决什么

`TODO.md` 的 M27 原本只有一句"全新（槽位 / `EquippedTo` / 类型校验 Observer / 穿脱），
并定下属性的「基础值 + 加成」结构"。本文把那句话拆成**可落地的决定**，
并把每条的**代价**说清楚——尤其第 5 节的属性叠加，它是"结构定错了后面全要改"的那一条。

## 二、三个实体角色

```text
PC（单位根）
 ├─ 槽位实体 EquipmentSlot { slot: SlotKind }     ← ChildOf(pc)：跟着 PC 动
 │    └─ （装上时）物品实体 Item { kind }          ← EquippedTo(slot)：逻辑归属
 └─ 属性组件（Health / Armor / BlockChance …）    ← 由"基础值 + 加成"算出
```

| 角色 | 是不是实体 | 关系 | 为什么 |
| :--- | :--- | :--- | :--- |
| **槽位** | 是 | `ChildOf(pc)` | PC 的物理延伸；跟着 PC 走是空间事实 |
| **物品** | 是 | `EquippedTo(slot)` | 逻辑归属：卸下时物品要活着（掉地上 / 进包） |
| **属性** | 否（组件） | — | 见第五节 |

槽位挂 `ChildOf` 而不是 `EquippedTo` 倒过来，理由见 [relations.md](relations.md) 第三节：
`ChildOf` 管"跟着动"，`EquippedTo` 管"装在哪个槽"。**一件物品可以只断逻辑不断空间**
（卸下时两步都做，但概念上是两件事）。

## 三、槽位集合 ❓ **需要你定**

这一版只给**最小可用集**，因为槽位是玩法取向而不是技术决定：

| 槽位 | 提供什么 | 备注 |
| :--- | :--- | :--- |
| `MainHand` 主手 | 动作节奏（`ActionTiming`）、伤害、`CombatTags`、解锁技能 | **决定"你是什么打法"** |
| `OffHand` 副手 | 格挡率（`BlockChance`）、护甲 | 盾 / 副武器 |
| `Armor` 身甲 | 护甲（`Armor`）、移速修正 | 最直接的防御线 |
| `Trinket` 饰品 | Focus 上限 / 回复速率 | **改资源线**，比改数值更有味道 |

**我建议先只做 `MainHand` + `Armor` 两个**，理由是它们分别验证两条不同的链路
（"装备改动作" vs "装备改抗性"），而副手 / 饰品是同一套机制换个数值，随时能加。
**要不要一次做全四个，你定。**

## 四、穿脱：三件事，一个 Observer

**穿上**（一次原子操作）：

```text
① 物品 insert EquippedTo(slot)   —— 逻辑归属（hook 自动维护 slot 的 EquippedItems）
② 物品 insert ChildOf(slot)      —— 空间附着（跟着槽位动）
③ 重算 PC 的属性                 —— 见第五节
```

**卸下**：

```text
① 物品 remove EquippedTo         —— 断逻辑
② 物品 remove ChildOf            —— 断空间
③ 把 GlobalTransform 写回 Transform —— **否则物品跳到世界原点**（最容易忘的一步）
④ 重算 PC 的属性
```

**校验只有一个入口**：`On<Insert, EquippedTo>` 的 Observer——

```rust
// 槽只收对的东西，不符合当场退回（并给一条拒绝理由给 HUD）
app.add_observer(|trigger: On<Insert, EquippedTo>, slots: Query<&EquipmentSlot>, items: Query<&ItemKind>| {
    // 槽类型 ≠ 物品类型 → 移除 EquippedTo
});
```

无论装备是被玩家拖上去、被 AI 装上、还是被脚本塞进去，都过这一个 Observer。
**拒绝理由要走消息**（与 `ActionBlocked` / `BlockRefused` / `MoveRefused` 同一条提示条），
不要让装备系统自己去写 UI。

## 五、属性叠加：**基础值 + 加成** ❓ **结构决定，代价最大**

这是 M27 唯一"定错了会连累别人"的地方：`can_cast` 与命中公式都要读属性，
结构变了它们得跟着改一遍（`docs/equipment.md` 原来就标着这条）。

### 候选 A：把加成写回组件（**不推荐**）

装备时直接 `Health.max += 10`，卸下时减回去。

- ✅ 改动最小，所有现有读组件的地方一行不改
- ❌ **卸下时减多少要靠"记住装上时加了多少"**，两处记账迟早对不上
- ❌ 基础值被永久覆盖，"我当时的基础护甲是多少"再也查不出来

### 候选 B：分两个组件（**推荐**）

```rust
/// 基础值：组装层给的，装备不动它
#[derive(Component)] pub struct BaseArmor(pub i32);
/// 加成：装备域维护的**唯一**写入者
#[derive(Component)] pub struct ArmorBonus(pub i32);
```

读取侧统一走一个纯函数：

```rust
/// 有效护甲 = 基础 + 加成。纯函数，零 Bevy，可单测
pub fn effective_armor(base: i32, bonus: i32) -> i32 { base + bonus }
```

- ✅ **基础值不变**，"没穿装备时我是什么样"随时可查（调试 / 卸下 / 重新计算都靠它）
- ✅ 加成只有一个写入者（装备域），符合"组件写入者唯一"那条铁律
- ✅ 加成的重算是**幂等的**：把 `ArmorBonus` 清空再加一遍，结果相同——
  不需要"记住上次加了多少"
- ❌ 每个可被装备影响的属性都要拆成两个组件；读取点要记得用 `effective_*`

### 候选 C：一张加成表（**过度设计**）

PC 身上挂 `Vec<AttributeBonus>`，读取时遍历求和。

- ✅ 最灵活（临时 Buff / 光环 / 装备共用一套）
- ❌ **现在只有装备一个来源**，为它引一张表 + 遍历是"为假想的需求设计"
  （项目自己的规矩：够用就不加机制）
- 触发条件：出现第二种加成来源（Buff / 光环）时再升级到 C，**B 到 C 的迁移是局部的**

**我推荐 B。** 要不要按 B 做，或者你更想要 C，**请拍板**——这条定了我才能动手。

## 六、装备"提供"什么：**数据来源，不是新机制**

装备不引入新的战斗机制，它是**往单位身上挂组件的来源**：

| 装备提供 | 效果 | 落到哪个组件 |
| :--- | :--- | :--- |
| 动作节奏 | **武器决定动作节奏** | `ActionTiming`（见第七节） |
| 伤害 | 攻击数值 | `PhysicalDamage` 等（同第五节：基础 + 加成） |
| 对抗标签 | 能不能被打断 / 招架 / 格挡 | `CombatTags` |
| 解锁技能 | "有剑才能用斩击" | `AbilityDef.requirements`（新增 `Requirement::HasSlot(SlotKind)`）🚧 |
| 抗性 | 护甲 / 格挡率 | `Armor` / `BlockChance`（第五节的结构） |

这条与设计总纲那条一致：**成长通过属性影响公式与条件，不改变系统结构**。

## 七、武器决定动作节奏 —— 与 `config/` 的关系 ❓

`config/actions.ron`（本次刚落地）里已经有每条技能的前摇 / 后摇。装备一把武器时，
"这把剑的重击比默认慢 0.2 秒"该记在哪？

| 方案 | 说明 | 代价 |
| :--- | :--- | :--- |
| **甲：武器覆盖整条 `ActionTiming`** | 装备域给 PC 写一个"当前武器节奏" | 简单；但"我只想改后摇"做不到 |
| **乙：武器给偏移量** | `WindupDelta` / `RecoveryDelta` 加成组件 | 与第五节的"基础 + 加成"同形，可组合；但多一层 |
| **丙：技能定义里加 `weapon_override`** | 技能表声明"这一手用武器节奏" | 数据驱动；但要改 `AbilityDef` 形状 |

**我倾向乙**：它和第五节的属性叠加是**同一个模式**（基础来自配置，武器给偏移），
不引入第二套心智模型。但这会让"配置里写的 0.3 秒前摇、装上剑变成 0.5"这种事
需要两处对账——**你如果想先简单点，选甲。**

## 八、与 `config/` 的分工（重要）

| 数值 | 住哪 | 为什么 |
| :--- | :--- | :--- |
| 技能的**基础**前摇 / 后摇 / 消耗 | `config/actions.ron` | 全局设计数据，与具体武器无关 |
| 武器的**偏移 / 覆盖** | 装备的定义里（将来的 `config/items.ron`） | 属于那一件物品 |
| 单位的**基础**护甲 / 血量 | 组装层（`spawn/`） | 与角色相关，不是技能也不是装备 |

**不要把一个数值同时放进两处**——这是本项目反复踩过的坑
（`SkillDef.label` 与 `SkillKind::label()` 曾逐字重复、`frame` 曾在技能表和载荷上各存一份）。

## 十、落地顺序（待你点头后）

```text
① 属性叠加结构（第五节 B）—— 先做它，因为它是别人依赖的那一层
② 槽位 + EquippedTo + 类型校验 Observer —— 机制本体
③ 穿脱与重算 —— 把①②接起来
④ 武器改节奏（第七节）—— 如果你选了乙
⑤ 装备到 PC 身上（组装层）+ HUD 显示 —— 可玩
```

`spawn/` 组装装备、`presentation` 只读显示，**都不新增领域**——
装备逻辑属于 `combat`（它改的全是战斗属性），或者独立一个 `equipment` 域？
**这也是个小决定**：我倾向**独立 `equipment` 域**，因为"槽位 / 物品 / 穿脱"
不是战斗概念（将来背包、掉落也要用它），而 `combat` 已经有 8 个子域了。
