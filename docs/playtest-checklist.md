## 2. 鼠标

- [x] 左键**空地**：走到那一格 —— 实测 `HoveredCell = (4,2)`（光标压在空地上、
      `PointerOverUi = false`），左键后玩家 `Cell (1,0) → (4,2)`，

- [x] 左键**单位**：用当前选中的技能打它（2026-09-27 验证成功）
      **做法**：先用**实测**求屏幕→格的映射（见文末"屏幕→格怎么量"），
      再把光标放到**敌人那一格的地面**上、左键。

      `HoveredCell` 是 `null`（射线打中的是纸片网格、不是地面），

      **"点谁打谁"的直觉与"点格子"的模型在这里不一致**——是设计还是缺陷，

## 3. UI 穿透（#46 的守门）——⚠️ **BRP 验不了，必须真人用真鼠标**

**2026-09-27 查明**：BRP 的合成光标**驱动不了 Bevy 的 UI 焦点**，所以这一节整节
**用 BRP 无法验证**（不是"还没验"，是"这条路验不了"）。直接证据：

- `world.query bevy_ui::focus::RelativeCursorPosition`（7 个区域根节点全查）
  → **每一个都是 `cursor_over: false`、`normalized: null`**——
  也就是说 Bevy 的 `ui_focus_system` **从没把光标当成压在任何 HUD 节点上**；
- 于是 `PointerOverUi`（依赖 `cursor_over`）在 BRP 输入下**恒为 `false`**：
  实测把光标放到玩家面板 / 技能栏 / 敌人列共 5 个点上，它一次都没变过 `true`；
- 更直接的对照实验：光标停在技能栏第 3 格中心、`MenuSelection.index = 0`，
  **点击前后都是 `0`**——点击根本没进节点（`Interaction` 需要
  `ui_focus_system` 先把光标认成悬停）。

**这与文末"已知坑 #2"是同一件事，但结论要更进一步**：不只是
"鼠标真的悬停在 UI 上验不了"，而是**这一整节（含"点面板世界不动"）都验不了**——
因为"面板吃掉了这次点击"这件事本身就要求 `cursor_over` 为真。

- [ ] 在每个面板上点一下，**世界不动**：玩家面板 / 敌人面板 / 技能栏 / 战斗日志
      （含标题与正文）/ 提示条 / 时间轴 / 帮助面板 —— **待人肉验证**
- [ ] 光标压在面板上时：`HoveredCell` 变 `None`、战场高亮与 AOE 预演**消失**、
      提示条收起、`PointerOverUi` 为 `true` —— **待人肉验证**
- [ ] `F1` 收起帮助面板后，世界立刻能再点（不能永久点不动） —— **待人肉验证**

⚠️ **替代手段是有的，但换的是问题**：这一节的对偶——"**点世界会真的下单**"——
**BRP 验得了**（实测左键点空地确实让玩家走过去了，见第 2 节），
所以"UI 门控把点击让给了世界"这一半只能靠真人。
`src/interaction/ui_capture.rs` 的单测覆盖了"`cursor_over` 为真/假时的行为"，
但它们**喂的是自己构造的组件值**，验不到"真光标能不能让 Bevy 把它置真"。

## 4. 冻结（三种原因都要能显示出来）

**2026-09-27 四种情形全部实机走通**（状态行原文照录）：

- [x] `awaiting`：玩家空闲 → 顶栏 `TIMELINE · FROZEN · awaiting`
- [x] `threat`：敌人前摇 / 投射物在飞 → `TIMELINE · FROZEN · threat`，战场上有威胁格
- [x] `manual`：**世界本该在跑**时按 `P` → `TIMELINE · FROZEN · manual`
      （#50 就是这里说反话；这是它修好之后第一次有画面证据）
- [x] 叠加时按字母序拼出来 → `TIMELINE · FROZEN · awaiting + manual`

⚠️ **要看到 `manual` 单独出现，必须先让"世界本该在跑"**：玩家空闲时按 `P`
**看不到** `manual`——因为清空原因后 `awaiting` 下一帧立刻断言回来（设计如此：
"放开世界"不等于"跳过决策"），`ManualPause` 根本没被置位。
本次的可复现手法：把玩家 `DecisionSlot` 改成 `{"Executing":{"until":99}}`（忙碌 →
不再断言 `awaiting`），再把威胁窗口 `ReactionSlot.resolved` 置 `true`
（让在飞的投射物落地、世界恢复运行），然后按 `P`。
⚠️ 顺带踩到：`ReactionSlot` 用的是**它自己的** `threat` 实体引用，
删掉敌人**不会**关窗（投射物仍在飞）——要关窗就置 `resolved`，或者真的表态。

### 已定性并修复：候场区 chip 亮着的那一个是**在飞的箭**

**现象**（2026-09-27，连续两次读数一致）：场上只有 **3** 个单位
（玩家 + 2 敌人），**三个的 `DecisionSlot` 全是 `Executing`**（都在忙、没有人"已就绪"），
而 4 个 `TimelineReadyChip` 里 **index 3 是 `display: Flex`（亮着）**、index 0/1/2 是 `None`。
chip 上写的字母是 `E`。

**代码路径**（`presentation/hud/timeline/system.rs:236-252`）：
```rust
let faction = model.ready.contains(&chip.index)          // chip.index 是**车道号**
    .then(|| model.lane_faction.get(chip.index).copied().flatten())
    .flatten();
```
而 `lane_faction` 来自 `lane_actor`，`model.ready`（`model.rs:271-280`）是
`lane_actor[*lane].is_some_and(|actor| ready.contains(&actor)) && lanes[*lane].is_empty()`
筛出来的车道号。**3 个单位时车道 3 不该有 actor**，因此它不该进 `ready`。

**两种可能，下轮用一条测试就能分开**：
1. **模型算错了**——`build_model` 在"全员忙碌"时仍给出非空 `ready`
   （那么 `ready.contains(&3)` 为真）。**判定**：直接单测 `build_model`：
   给一个全员 `Executing` 的 roster，断言 `model.ready.is_empty()`。
   这是最省的一步，且不需要起游戏。
2. **UI 写错了**——模型是对的（`ready` 为空），但 chip 的显隐没被重写
   （`TimelineCache` 的比对漏了 `ready`？—— 但 `matches()` 里明明有
   `cache.ready == self.ready`，所以这条可能性低）。
3. 还有一种可能：`chip.index` 不是车道号而是"第几个就绪者"。
   读 `scene.rs` 里 chip 的构造即可确认。

**结论（2026-09-27，已修）**：不是第 1 种（模型没算错），也不是陈旧帧——是
**`Faction` 被当成了「单位」的判据**。`combat::attack::scene` 给箭矢 / 横扫 / 火球
都烘了 `Faction`（供命中过滤），而时间轴的 `actors` 查询只要 `Faction` 就算单位，
于是**一支在飞的箭**占了一条车道；它没有 `DecisionSlot`，而"没有决策槽"按定义
**算已就绪**，于是它站上了候场区、亮出 `E`。
**修法**：那条查询加 `With<Health>`（单位都有、攻击实体都没有；
`combat::attack::explosion` 找"可被炸到的身体"用的也是这一条）。
**验收**：新增 `attack_entities_are_not_units`——**实测它在松查询下会转红**
（报"箭矢不是单位：它不该占车道…"）、加回 `With<Health>` 后通过。
⚠️ **根因是全局性的**：另有约 10 处"按 `Faction` 枚举单位"的松查询
（镜头跟随 / 点击拾取 / 敌人瞄准 / 悬停占位…），已审计成表记在
[`backlog/dev.md`](backlog/dev.md)，**不要在别处再单独修一处**。

### 屏幕 → 格怎么量（别再目测推算）

**2026-09-27 的教训**：照截图目测坐标推算敌人位置，两次自相矛盾还不自知，
于是把"探点全落空"误读成"悬停回归"。**目测推算不是测量。**

**可靠做法（三点定局部线性映射）**：起游戏后，在**已知良好的空地**上取三个点读
`HoveredCell`，解出两个基向量，再外推到目标格。实测那一轮的三个点：

| 物理像素 | → 格 |
| :--- | :--- |
| `(960, 540)`（近屏幕中心） | `(2, 0)` |
| `(700, 540)`（左移 260） | `(1, 2)` |
| `(960, 660)`（下移 120） | `(3, 1)` |

即 **左移 260px ≈ 格 (−1, +2)**、**下移 120px ≈ 格 (+1, +1)**。
按它们解 `(2,0) → (3,3)`（需 `Δ格 = (+1,+3)`）得到屏幕点 **`(787, 740)`**，
实测读回的正是 **`cell (3,3)`** ✅ ——与敌人的格完全一致。

⚠️ **注意映射是投影的、不是线性的**：外推距离越远越偏（同一次里按另一组梯度
算 `(1133,740)` 得到的是 `(5,1)`，差了 2 格）。所以**解出来的点必须回读验证**，
不要直接信算出来的坐标。相机每轮开局都吸附在同一位置，所以这三个点可以复用。

## 已知坑（别重复踩）

1. **MCP 注入输入的"松手"依赖时钟**：`bevy_brp_extras` 的按键松手按时钟计，
   而这个世界大部分时间是冻结的 → 松手定时器不到点 → 那个键**一直是按下状态**，
   **同一个键按第二次不会触发 `just_pressed`**。
   看到"某个键没生效"时，先确认它不是"还按着"：按一下空格让世界跑一秒，再试。
2. **BRP 的合成光标驱动不了 Bevy 的 UI 焦点**（`ui_focus_system` 每帧重算）：
   实测 7 个区域根节点的 `RelativeCursorPosition.cursor_over` **全是 `false`**、
   `normalized` 全是 `null`，于是 `PointerOverUi` 在 BRP 输入下**恒为 `false`**、
   点技能格也不改变 `MenuSelection`。
   ⚠️ **结论比早先写的更强**：不只"悬停在 UI 上"验不了，第 3 节整节
   （含"点面板世界不动"）都**验不了**——那要求 `cursor_over` 为真。
   早先这里写的是"实机能验的是 `PointerOverUi` / `HoveredCell` 这类我们自己的资源"，
   **那句是错的**：`PointerOverUi` 恰恰依赖那个为假的 `cursor_over`。
   **真实验得了的**：世界拾取（`HoveredCell`）与"点世界会下单"——它们读窗口光标，
   与 UI 焦点不是同一条路。
3. **别把按键造成的状态变化算到鼠标头上**：`W` / `Q` 这类技能键**自己会设
   `MenuSelection`**，所以"点完格子发现 `MenuSelection` 变了"可能根本不是点击的功劳
   （2026-09-27 就是这么误判过一次，见第 7 节"技能槽点击"那条）。
   判断鼠标有没有生效，**要先看 `cursor_over`**；那个为假时，一切 UI 点击结论都不成立。
4. **查不到 ≠ 不存在**：没派生 `Reflect` 的组件在 BRP 里等于不存在，`world.query`
   会**静默返回空**。排查"东西没生成"之前先确认它进了反射表
   （有测试 `the_diagnostic_anchors_are_reflected` 守着）。
